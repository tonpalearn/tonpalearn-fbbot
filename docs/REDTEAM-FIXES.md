> วิธีอ่าน: 🔴 = ห้ามขึ้นจริงจนกว่าจะแก้ · 🟠 = ควรแก้ก่อนเปิดให้คนนอก · 🟡 = แก้ทีหลังได้

## ข้อสรุปที่แรงที่สุดจากการสอบทาน

> "47 เทสต์เขียวเพราะ mock ทับชั้นฐานข้อมูลกับชั้นโมเดลทั้งก้อน — ของที่พังอยู่นอกชั้นที่เทสต์ครอบทั้งหมด"

ถูกต้อง และเป็นบทเรียนที่ต้องจำ: **เทสต์ที่ปลอมทุกอย่างที่ออกนอกเครื่อง จะไม่มีวันจับบั๊กที่อยู่ตรงรอยต่อ**
บั๊กที่ร้ายที่สุด 2 ข้อ (B1 หน้าเว็บพัง, B2 ค้นหาไม่เจอ) อยู่ตรงรอยต่อพอดี

## 🔴 blocker — แก้แล้วทั้ง 6 ข้อ

| # | อาการ | สาเหตุจริง | แก้ยังไง |
|---|---|---|---|
| **B1** | หน้าแชทของแอดมินขาวทันทีที่กดเปิด | API คืน `{conversation:{...}}` แต่หน้าเว็บอ่าน `data.messages` ตรง ๆ · TypeScript จับไม่ได้เพราะเป็นแค่ generic cast | คืนออบเจกต์ตรง ๆ ตาม contract ใน SPEC §10 |
| **B2** | บอตตอบ "ขอส่งต่อให้ทีมงาน" กับเกือบทุกคำถาม | `similarity()` คิดจากสัดส่วนต่อความยาวรวมสองฝั่ง — คำถาม 25 ตัวอักษรเทียบท่อน 800 ตัวอักษร ได้ ~0.03 เสมอ **ต่อให้ตรงทุกคำ** ⇒ ชั้นฐานความรู้ไม่เคยคืนอะไรเลย และชั้นคำถามที่ถามบ่อยก็ตกเกณฑ์แม้เจอคำสำคัญตรง ๆ | เปลี่ยนเป็น `word_similarity()` + ตัวดำเนินการ `<%` (ออกแบบมาสำหรับสั้น→ยาว) และให้คะแนนพื้น 0.75 เมื่อเจอคำสำคัญตรงในข้อความ |
| **B3** | โอนสายไม่สำเร็จ → บอตพูด "กำลังเรียกทีมงาน" ซ้ำไม่รู้จบ | ส่งข้อความ → เรียก Facebook → **ค่อย**ตั้งสถานะ · ถ้ากลางทางล้ม สถานะไม่เคยถูกตั้ง | สลับลำดับ: ตั้งสถานะ+บันทึกก่อน แล้วค่อยเรียก Facebook ใน try/catch · ถ้าล้มให้เขียนข้อความจากระบบบอกแอดมินว่าเกิดอะไรขึ้น |
| **B4** | ข้อความลูกค้าหายระหว่างที่คนถือสาย | Facebook ส่งมาทาง `entry.standby[]` ไม่ใช่ `entry.messaging[]` — โค้ดวนแค่ช่องเดียว | เพิ่มลูปอ่าน `standby` แล้วบันทึกอย่างเดียว ไม่ตอบอะไรออกไป |
| **B5** | ลูกค้าเห็น "กำลังพิมพ์" แล้วเงียบตลอดกาล | ประวัติแชทที่ส่งเข้าโมเดลไม่ถูกรูปแบบ (ขึ้นต้นด้วยฝั่งบอต / ฝั่งเดียวกันติดกัน / มีข้อความว่าง) → API ปฏิเสธทั้งคำขอ | เพิ่ม `normalizeHistory()` + เทสต์ 5 เคส |
| **B6** | กดปิดบอตแล้วบอตไม่ดับ แต่หน้าเว็บบอกว่าบันทึกแล้ว | ตาราง `fb_pages` ว่าง · `update` 0 แถวไม่ถือเป็น error | เปลี่ยนเป็น `upsert` + เพิ่มแถวเพจใน seed + เพิ่มขั้นตอนใน DEPLOY |

## 🟠 แก้แล้ว 8 ข้อ

| # | เรื่อง | แก้ยังไง |
|---|---|---|
| O1 | ฟังก์ชันถูกตัดจบ → ข้อความหายถาวรเพราะกันซ้ำบล็อกไว้ | ถ้าแถวเดิมค้างสถานะ `processing` เกิน 2 นาที ให้ลองใหม่ได้ + ตั้ง `maxDuration = 60` |
| O2 | `mark_seen` ล้มเดียว ทำให้ไม่ตอบลูกค้าเลย | ห่อด้วย `.catch(() => {})` — เป็นลูกเล่น ไม่ควรมีอำนาจฆ่าคำตอบ |
| O3 | เพดานค่าโมเดลรั่ว | `await` การบันทึกโทเคน · อ่านไม่ได้ให้ถือว่าเต็มเพดาน (fail-closed) · นับ "วันนี้" ตามเวลาไทย ไม่ใช่ UTC |
| O4 | "ไม่สนใจครับ" ถูกลากเข้ากระบวนการขอเบอร์ | เพิ่มกติกา "ไม่สนใจ" ที่ลำดับ 5 (มาก่อน) · เปลี่ยน `'แอดมิน'` เป็น regex เจาะจง · เมนูใช้ `exact` |
| O5 | แอดมินพิมพ์ตอบแล้วบอตยังแย่งตอบทับ | ตอบเองครั้งแรก = ตั้งสถานะ `human_active` อัตโนมัติ |
| O6 | ฟังก์ชันอยู่อเมริกา ฐานข้อมูลอยู่สิงคโปร์ | เพิ่ม `vercel.json` → `{"regions":["sin1"]}` |
| O8 | `[กรอกเอง]` รั่วออกทางฐานความรู้ | กรองท่อนที่มีคำนี้ทิ้งก่อนส่งเข้าโมเดล |
| O9 | ไม่มีตาข่ายรับคำตอบ พึ่งพรอมป์อย่างเดียว | เพิ่ม `lib/guard.ts` — ถ้าคำตอบมีราคา/วันที่/เวลา ที่ไม่ปรากฏในเนื้อหาอ้างอิง **ห้ามส่งออก** ให้โยนหาคนแทน (13 เทสต์) |
| O11 | SPEC เคลมว่ามีตัวกันเดารหัส 10 ครั้ง/5 นาที ทั้งที่บน Vercel ใช้ไม่ได้จริง | แก้ SPEC ให้ตรงความจริง + **บังคับรหัสยาวอย่างน้อย 16 ตัว** ที่ระดับโค้ด |

## ข้อที่ต้องไปยืนยันกับของจริง (ยังฟันธงไม่ได้จากการอ่านโค้ด)

1. **`standby` array** — เพิ่มโค้ดอ่านไว้แล้ว (ไม่มีต้นทุนถ้าไม่มีข้อมูลมา) แต่ต้องยืนยันด้วยการดู payload จริงจากเพจจริงหลังโอนสาย 1 รอบ
2. **ใครได้ event `pass_thread_control`** — ตอนนี้สลับสถานะทันทีโดยไม่เช็ก `new_owner_app_id` ถ้าเพจมีแอปอื่นอยู่ด้วยควรเช็กเพิ่ม
3. **สิทธิ์ HUMAN_AGENT** — ต้องรู้ว่าจะขอหรือไม่ ก่อนจะรู้ว่าข้อความ 422 จะโผล่บ่อยแค่ไหน
4. **เวอร์ชัน Graph API ที่ควรใช้** — ต้องเปิด changelog อ่าน ณ วันที่ deploy

รับข้อสอบทานทั้งหมด ไม่มีข้อไหนที่เถียง — รวมทั้งข้อที่ติงว่า PROGRESS.md เขียนคำว่า "เสร็จ" กว้างกว่าความจริง
**แก้ถ้อยคำในเอกสารแล้ว:** หลักฐานเดิม 10 ข้อเป็นการยิง HTTP ระดับสถานะ ไม่ได้พิสูจน์ว่าข้อความหนึ่งชิ้นเดินจนสุดทาง
รอบนี้เพิ่มการทดสอบผ่านหน้าเว็บจริงในเบราว์เซอร์ (ล็อกอิน → หน้าภาพรวม → หน้ากติกา → กดปุ่มทดลอง → ได้คำตอบถูกต้อง)

**สิ่งที่ยังพิสูจน์ไม่ได้จนกว่าจะมีฐานข้อมูลและเพจจริง** (ต้องเดินตารางทดสอบใน `docs/DEPLOY.md` ขั้นที่ 7 ให้ครบ 8 แถว):
- หน้าแชทที่มีข้อมูลจริง (B1 แก้แล้วแต่ยังไม่ได้เห็นข้อความจริงในหน้าจอ)
- คุณภาพการค้นหาหลังแก้ B2 — **ต้องทดสอบด้วยข้อความจริงที่คนไทยพิมพ์ 20 ประโยค แล้วนั่งอ่านผลทีละข้อ** ก่อนเชื่อว่าใช้ได้
- การโอนสายกับ Page Inbox ของจริง
